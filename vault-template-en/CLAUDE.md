# engineering-vault conventions

This is the user's personal engineering knowledge base: an Obsidian vault that is also a git repository. Your job (Claude) here is to help the user record, tidy and retrieve — not to rewrite the user's content. Read this whole file before doing anything.

## Layout

```
inbox/               quick notes, when you do not know where something belongs; tidy weekly
projects/<project>/  one folder per project (ProjectA, ProjectB …); sub-folders are allowed
knowledge/<topic>/   general, reusable knowledge, including conclusions Claude looked up (embedded, electronics, c, docker, git, ai …)
_templates/          Obsidian templates
_attachments/        images and other attachments
scripts/             build_index.py, lint.py, new_note.py, sync.ps1, githooks/
_local/              not committed (.gitignore); for sensitive or confidential material (employer, customer data …)
Index.md             generated overall index
projects/*/_index.md, knowledge/_index.md   generated, never edit by hand
```

Create topic folders as needed, in lowercase English. Inside a project, use the frontmatter `type` to tell note / debug / decision apart.

## Free-form writing, tidy later

The user may create or edit any md file directly in `projects/<project>/` (sub-folders included) or `inbox/`, in any format, without running any command.

- Notes without frontmatter or a dated file name are still indexed; their status column shows "untidy". lint treats them as warnings, not errors.
- The index is generated by `python scripts/build_index.py`. The repo's pre-commit hook (`scripts/githooks/pre-commit`, needs `git config core.hooksPath scripts/githooks` run once) refreshes it on every commit; before searching, summarising or tidying in a session, run it once yourself so the index reflects what is on disk.
- No background process changes notes when the user is not acting. Tidying only happens when the user asks (or you are asked to in the session).

### Tidying a project (user says "tidy ProjectA", "organise this")

1. `git status` to check the working tree; run `python scripts/lint.py` and list the untidy notes and why.
2. Read each one. At most 20 per batch. Give a proposal table: `file | proposed file name | proposed type | proposed title and summary | tags | proposed [[links]] | possible duplicate of | action (default accept)`.
   - Proposed file name: `YYYY-MM-DD-topic.md`. Prefer a date written in the note body, otherwise the first-commit date from `git log --diff-filter=A --format=%as -- <file>`.
   - `project` must match the project folder.
3. **Wait for the user's confirmation.** The user can answer accept / modify / merge / skip per row. Without confirmation, change no file.
4. For confirmed items: rename with `git mv`; only add frontmatter at the top, never rewrite the body; mark the summary, tags etc. you wrote with `ai_generated: true`, `reviewed: false`; only append links to the "Related" section.
5. Run `python scripts/build_index.py` and `python scripts/lint.py`, commit per the sync rules, and report how many were processed and skipped.

For `inbox/` use the `triage-inbox` skill.

## Naming (tidy notes)

- File name: `YYYY-MM-DD-topic.md`; the date is the day first recorded and never changes.
- Topic in lowercase kebab-case, without spaces or `\ / : * ? " < > |`.
- File names must be unique across the vault; wikilinks use the file name only: `[[2026-10-05-st25dv-gpo-debug]]`, or `[[file-name|display name]]` for a display name.
- Files starting with `_` are generated or system files, not notes.

## Frontmatter (tidy notes)

```yaml
---
title: ST25DV GPO does not trigger
type: debug              # note | debug | decision | knowledge
project: ProjectA        # required under projects/, must match the folder; optional for knowledge
summary: one-line key point, used for the index and search
status: solved           # optional: draft | active | solved | accepted | superseded
tags: [nfc, embedded]
created: 2026-10-05      # first recorded date, never changes
updated: 2026-10-05      # update whenever the content changes
source: self             # self | claude; required for knowledge
ai_generated: false      # true for content Claude wrote
reviewed: true           # starts false when ai_generated is true; set true after the user confirms
---
```

## Project notes vs knowledge

- A project note records "what happened in this project": symptoms, investigation, decisions, context at the time.
- Knowledge records "facts useful in any future project": principles, rules, pitfalls, commands.
- When a debug note yields a reusable conclusion, write (or append to an existing) knowledge note and `[[link]]` the two both ways.
- A conclusion supported only by the user's own testing, with no outside source, gets a callout: `> [!warning] Tested by me only; not verified by an external source`.

## Tracking time

- `created` never changes; update `updated` when content changes.
- Append a line to the "Changelog" section for important edits: `- 2026-10-12 added the oscilloscope findings`.
- Git history is the authority on time: `git log --follow <file>` shows a note's whole evolution.

## Saving knowledge Claude looked up

When the user says "save this to notes" or similar, use the `save-knowledge` skill:

- Save conclusions, steps, key reasons and source links — not chat transcripts.
- Write to `knowledge/<topic>/` with `source: claude`, `ai_generated: true`, `reviewed: false`.
- Search for an existing related note first; if there is one, append and update `updated` instead of creating a duplicate.
- If related to a project, link both ways between the knowledge note and the project note.
- In a session inside the vault, save when the user asks. In sessions in other projects, if the user installed the user-level hook (see `_meta/user-level/README.md`), Claude checks before each turn ends and saves general knowledge automatically; those notes are also `ai_generated: true`, `reviewed: false`, awaiting the user's review.

## Search and summaries

- First run `python scripts/build_index.py`, read `Index.md` and the relevant `_index.md`, narrow down with `summary`, then read the bodies. Untidy notes have no summary; read their bodies directly.
- To summarise a period: read the project's `_index.md`, add `git log --since=<date> -- projects/<project>`, then read the notes involved. Do not write from impression.
- By default give the summary only in the conversation; write it as a note only if the user asks.

## Hard rules

1. Never delete notes or attachments. When clean-up is needed, list candidates for the user.
2. Never overwrite the content of an existing note. Edit existing notes only locally or by appending, and keep the original information.
3. Move or rename only with `git mv`, and show the plan (old path → new path) for confirmation first.
4. When you find duplicate or very similar notes: report them and propose a merge; wait for approval; do not merge on your own.
5. When unsure where something belongs, leave it in `inbox/`; do not guess.
6. Never hand-edit the generated index files; re-run the script after changing notes.
7. Never write passwords, tokens, internal addresses or customer information into notes. If you find such content in the user's notes, warn the user and suggest moving it to `_local/`.
8. Never `git push --force`, `git reset --hard` or `git clean`.

## Sync rules

The Obsidian Git plugin commits automatically on a timer (once a day by default, and the user may trigger it by hand at any time), so run `git status` before you start and never overwrite uncommitted user changes.

After you change notes:

1. `python scripts/build_index.py`, then `python scripts/lint.py`; fix errors first (untidy is only a warning).
2. `git add` the specific files, not `git add -A`.
3. Commit message format: `vault: <action> <object>`, e.g. `vault: add debug note st25dv-gpo`.
4. If there is an `origin`, `git push`; if the push fails, tell the user honestly and never force-push. Without `origin`, commit locally only.
